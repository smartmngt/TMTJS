# 상권 지도 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 카카오 지도에서 상권을 누르거나 원을 그리면 유동인구·주거인구·가구 수·가구 형태와 순위를 보여 주고, 담은 곳을 비교하는 정적 페이지 `/TMTJS/map/`.

**Architecture:** `tools/build_map_data.py`가 서울 열린데이터·data.go.kr 원자료를 받아 `map/data.json` 하나로 정리한다. 페이지는 그 파일만 읽고, 원 안 숫자는 브라우저에서 20m 간격 점을 찍어 상권/동 밀도를 더한다(넓이 비례).

**Tech Stack:** Python 3 + pyshp + pyproj (빌드만), 바닐라 JS ES 모듈, 카카오맵 JS SDK, node:test.

**Spec:** `docs/superpowers/specs/2026-11-13-area-map-design.md`

## Global Constraints

- 기준 분기: 원자료 최신 분기(지금 `20262`). 하루 평균 = 분기 합계 ÷ 91.
- 좌표: 원자료 EPSG:5181 → 위경도(EPSG:4326), 소수 5자리.
- 화면: 배경 `#0C1017`, Pretendard, 세로 휴대폰 우선, 한국어.
- 새 의존성은 빌드 스크립트의 pyshp·pyproj만. 페이지는 외부 라이브러리 없이 카카오 SDK만.
- 원자료 캐시는 `tools/.cache/`(커밋 안 함).

## 설계에서 바뀐 점 (빌더 몫이던 3번 결정)

- 집계구 생활인구는 2026-07-31에 생산 종료, 250m 격자는 구 단위 합계만 공개 → **원은 동+상권 넓이 비례(상권 안은 상권 밀도, 나머지는 동의 남은 밀도)**로 계산. 원과 골목 숫자가 같은 기준(길단위 유동인구·상주인구)이 된다.
- 가구 형태: data.go.kr `국가데이터처_SGIS_가구집계구집계_20231231`(15159227)를 동 이름으로 합산. 유형: 1인가구 / 1세대가구 / 2세대가구 / 3세대가구 / 비혈연가구.

## Review Focus

1. 상권이 두 동에 걸쳐 남은 밀도가 음수 → 0으로 자르고, 자른 동 수를 빌드 로그에 출력.
2. 관광특구(6곳)는 다른 상권과 겹침 → 원 계산 밀도에서 제외(표시·순위는 포함).
3. 원이 한강·서울 밖에 걸침 → 해당 점은 0으로 더하고, 숫자는 정상 출력.
4. 2023 가구 자료의 동 이름이 지금 동 이름과 다름 → 못 맞춘 동 목록 출력, 가구 형태 칸은 "자료 없음".
5. 담은 목록 저장소가 막힌 브라우저(사생활 모드) → 오류 없이 이번 방문 동안만 유지.

### Task 1: 데이터 빌드 스크립트

**Files:**
- Create: `tools/build_map_data.py`, `.gitignore`
- Output: `map/data.json`

**Interfaces:**
- Produces `map/data.json`:
  ```
  { "q": "20262", "hhYear": 2023,
    "seoul": { "foot": 일평균합, "resid": 합, "hh": 합, "area": m² },
    "trdar": [ { "c": 코드, "n": 이름, "k": 종류명, "d": 동코드,
                 "foot": 일평균, "resid": n, "hh": n, "area": m²,
                 "rings": [[lng,lat,lng,lat,...], ...] } ],
    "dong":  [ { "c": 동코드, "n": "구 동", "foot", "resid", "hh", "area",
                 "rest": { "foot", "resid", "hh", "area" },
                 "types": { "1인가구": n, "1세대가구": n, "2세대가구": n, "3세대가구": n, "비혈연가구": n } | null,
                 "rings": [...] } ] }
  ```
  `rest` = 동 값 − 그 동에 속한 상권(관광특구 제외) 값의 합, 0 미만은 0.

- [ ] **Step 1:** 받기 함수 `fetch(url, data, dest)` — curl 대신 `urllib`, 4회 재시도(연결 끊김 대비). 받을 것: 영역-상권 SHP(OA-15560 seq 5 infSeq 3), 영역-행정동 SHP(OA-22160 seq 1 infSeq 3), 시트 CSV(OA-15568, OA-15584, OA-22178, OA-22183: `datafile.seoul.go.kr/bigfile/iot/sheet/csv/download.do`), 가구 CSV(data.go.kr 토큰 → `fileDownload.do`).
- [ ] **Step 2:** 정리: 최신 분기 행만, cp949 CSV, 좌표 변환, 경계 단순화(Douglas–Peucker 8m).
- [ ] **Step 3:** 끝 자체 점검(assert):
  - 공덕동 하루 유동인구 `round(foot) == 131237`, 가구 `18559`; 반포4동 `55522`, `7024`.
  - 상권 1,600곳 이상이 숫자와 경계 모두 있음, 동 425곳.
  - 가구 형태 매칭 동 400곳 이상.
  - `data.json` 3MB 미만.
- [ ] **Step 4:** 실행 `python3 tools/build_map_data.py` → `OK` 출력과 assert 통과.
- [ ] **Step 5:** 커밋.

### Task 2: 원 계산·순위 모듈

**Files:**
- Create: `map/calc.js`, `map/calc.test.mjs`

**Interfaces:**
- `circleStats(data, lat, lng, radiusM) -> { foot, resid, hh, area, types }` — 20m 간격 점, 점마다 상권(관광특구 제외) 안이면 그 상권 밀도, 아니면 동 `rest` 밀도 × 400m².
- `trdarRank(data, code, key) -> { rank, total }` — key ∈ foot/resid/hh, 큰 값이 1위.
- `seoulRatio(data, stats, key) -> number` — 원 값 ÷ (서울 합 × 원 넓이 ÷ 서울 넓이).

- [ ] **Step 1:** 테스트 작성: 1km×1km 정사각 동 하나(foot 1,000,000, rest 전부) 중앙에 반경 100m 원 → `foot`가 π·100²/10⁶×1,000,000 ±5%. 원이 동 밖으로 반쯤 나가면 약 절반. 상권 안 원은 상권 밀도 사용. `trdarRank` 1·2위 확인.
- [ ] **Step 2:** `node --test map/calc.test.mjs` → 실패 확인.
- [ ] **Step 3:** 구현.
- [ ] **Step 4:** 테스트 통과.
- [ ] **Step 5:** 커밋.
